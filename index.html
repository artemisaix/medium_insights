Claude Code — Como usarlo bien en equipo
Fuente: "Stop Treating CLAUDE.md Like a Prompt File" — Medium, Mar 2026
📄
1. El CLAUDE.md debe ser corto — maximo 50 lineas
CRITICO El error mas comun del equipo
  • Si el archivo tiene mas de 50-80 lineas, Claude empieza a ignorar partes. El volumen no ayuda, confunde.
  • El CLAUDE.md raiz debe tener solo 3 cosas: para que sirve el servicio (2 parrafos), mapa de directorios importantes, y comandos esenciales del proyecto.
  • Ejemplo real: Purpose + Structure + Rules + Common Commands. 20 lineas en total. Hace todo lo necesario.
  • Resistir el impulso de documentar cada caso borde ahi. Claude puede pedir mas contexto cuando lo necesite.
🛠️
2. Crear .claude/skills/ — workflows que se reusan, no se repiten
PRODUCTIVIDAD Estandariza el trabajo del equipo
  • Crear la carpeta .claude/skills/ con archivos Markdown para cada tarea repetitiva del equipo.
  • Skills recomendados: code-review.md (checklist de PRs), refactor.md (pasos estandar), debug-prod.md (investigacion de incidentes), api-design.md (convenciones REST).
  • Uso: "Revisa este PR usando el skill code-review". Claude sigue el mismo checklist siempre, sin variacion entre sesiones ni personas.
  • Beneficio clave: el conocimiento del equipo queda en el repo, no en la cabeza de cada persona.
# .claude/skills/code-review.md
Cuando revises codigo, verificar siempre:
1. Tests — tiene tests? cubren edge cases?
2. Error handling — que pasa si esto falla?
3. Performance — hay N+1 queries? loops innecesarios?
4. Seguridad — toca datos de usuario? auth? pagos?
5. Docs — las funciones nuevas tienen docstrings?
🪝
3. Configurar .claude/hooks/ — automatizacion que no depende de memoria
AUTOMATIZACION Claude olvidara. Los hooks no.
  • Los hooks son scripts que corren automaticamente en puntos clave, sin que nadie tenga que recordar pedirle a Claude.
  • Hook post-edicion: correr gofmt y go vet automaticamente sobre archivos editados en Go.
  • Hook de proteccion: si Claude toca un archivo de auth, billing o migrations → bloquear y pedir revision manual explicita.
  • Hook pre-commit: correr los tests relacionados con los archivos modificados.
  • Resultado: dejan de babysitear a Claude. El proceso se vuelve deterministico.
📁
4. CLAUDE.md local en modulos de alto riesgo
SEGURIDAD Para modulos sensibles del sistema
  • Poner un CLAUDE.md dentro de cada modulo riesgoso (auth, pagos, integraciones criticas de MeLi). Claude lo lee justo cuando trabaja ahi.
  • Que poner adentro: que NO se puede tocar sin aprobacion, compliance que aplica, gotchas conocidos del modulo, que tests son obligatorios antes de hacer un PR.
  • Mucho mejor que tratar de recordar todas las reglas de todos los modulos en el CLAUDE.md raiz.

Agent Teams en Claude Code — Multi-agente ya disponible
Fuente: "Anthropic Hid a Multi-Agent System Inside Claude Code" — Medium, Mar 2026
Que es esto?

Desde febrero 2026, Claude Code tiene un sistema de agentes en equipo: un agente coordinador planifica y delega, agentes especialistas trabajan en paralelo y simultaneamente en backend, tests, base de datos, etc. Una tarea de 90 minutos puede tomar 25-35 minutos.

🚀
Como activarlo y usarlo correctamente
NUEVO · Feb 2026
  • Activacion: una sola linea en el settings del proyecto. Ya esta construido en el binario.
  • Regla critica — Shift+Tab despues de aprobar el plan: bloquea al coordinador en modo "solo coordinar". Sin esto, el coordinador empieza a escribir codigo el mismo y rompe la arquitectura del equipo.
  • Sweet spot probado por Anthropic: 4 agentes especialistas, 5-6 tareas cada uno = 20 unidades de trabajo. Equipos de mas de 5 agentes generan overhead que cancela el beneficio.
  • Los agentes se comunican entre si directamente. El agente backend puede avisar al de tests que termino su parte sin pasar por el coordinador.
  • No intentar reanudar sesiones interrumpidas. Si algo se corta, crear un equipo nuevo desde cero.
// .claude/settings.json — activacion en una linea
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}

Cuando usar cada modo de Claude Code

4 agentes = 4x el costo en tokens. Ganan tiempo, no dinero de API. Usar para tareas donde el tiempo importa mas que el costo de tokens.

MCP (Model Context Protocol) — El nuevo estandar de integracion AI
Fuente: "From REST to MCP: Why Developers Should Embrace the Model Context Protocol" — Medium, Ene 2026
Por que importa para su equipo?

El modelo antiguo de integrar AI con servicios internos escala mal: M agentes x N servicios = M×N integraciones custom que mantener y que se rompen. MCP resuelve esto: un servicio se expone una vez y cualquier agente que soporte el protocolo lo puede usar sin codigo adicional. Ya lo adoptaron ChatGPT, VS Code, GitHub Copilot, Cursor y mas de 10,000 servidores publicos en 2025.

⚖️
REST vs MCP — Diferencia concreta para el dia a dia
REST tradicionalCon MCP
Cada integracion requiere codigo customSe configura una vez, cualquier agente la usa
El agente necesita aprender la forma de cada APIEl agente pregunta que podes hacer y el server responde
Coordinar multiples llamadas = responsabilidad del devEl agente orquesta los pasos solo
Credenciales pueden quedar expuestas al agenteLas credenciales se inyectan server-side, el agente nunca las ve
Debug: revisar N sistemas distintosUn unico punto central de auditoria
🔧
Consejo practico: usar Unla (MCP Gateway) para no reescribir nada
ACCION INMEDIATA Sin modificar servicios existentes
  • No hay que migrar las APIs REST existentes. Usar Unla (open source, escrito en Go) que toma endpoints REST y los expone como MCP via un archivo YAML de configuracion.
  • Cero cambios en el servicio original. Unla vive encima de los sistemas existentes como capa de traduccion. Se levanta con un comando Docker.
  • Viene con interfaz web para configurar y probar integraciones en vivo, sin codigo.
  • Ejercicio concreto: elegir un servicio Go interno → exponerlo con Unla → probarlo desde Claude Code. Lleva menos de una tarde.
  • Caso de uso que esto habilita sin codigo adicional: un agente busca un ID en BD → consulta otro servicio interno con ese ID → publica el resultado en Slack. Todo orquestado por el agente a traves de MCP.
🔒
Seguridad de MCP en Produccion
Fuente: "Securing the Model Context Protocol (MCP): Risks, Controls, and Governance" — Medium, Dic 2025
🛡️
Reglas antes de exponer servicios internos via MCP en produccion
CRITICO para MeLi
  • Nunca pasar credenciales directamente al agente. Usar un gateway (como Peta) que inyecta las credenciales server-side en cada llamada. El agente nunca ve las API keys reales, aunque el log de conversacion se filtre.
  • Definir politicas explicitas a nivel de gateway, no en el prompt: que puede leer el agente, que puede escribir, que requiere aprobacion humana antes de ejecutar.
  • Principio de minimo privilegio: si el agente solo necesita leer ordenes, no darle permisos de escritura ni eliminacion.
  • Toda accion queda en el log del gateway. Esto es auditabilidad real, no confiamos en el prompt. Para MercadoLibre, este trail de auditoria es indispensable.
  • Para sistemas criticos (pagos, datos de usuarios, infraestructura): configurar aprobacion humana explicita antes de que el agente ejecute acciones de escritura.

Golang + AI — Integrando LLMs en microservicios Go
Fuente: "Go + AI: Build LLM-Powered Microservices" y "The Observability Stack Every LLM-Powered Go Service Needs" — Medium 2025/2026
⚙️
Como conectar un servicio Go a un LLM
TECNICO Implementacion directa
  • Usar el SDK github.com/sashabaranov/go-openai. Compatible con cualquier API que siga el estandar OpenAI, incluyendo la API de Anthropic (Claude). Lo dificil no es conectarse, es hacerlo bien en produccion.
  • Estructura recomendada: Endpoint REST → AI Middleware (llama al LLM) → Response Handler (estructura y devuelve).
  • Casos de uso concretos para MeLi: clasificar tickets de soporte, resumir logs de errores, sugerir resoluciones a partir de stack traces, asistente de documentacion interna.
  • Framework recomendado: GoFr (open source) tiene OpenTelemetry, circuit breaker y health checks pre-integrados para servicios externos incluyendo LLMs.
// Integracion basica Go + LLM
client := openai.NewClient("API_KEY")
resp, err := client.CreateChatCompletion(ctx,
  openai.ChatCompletionRequest{
    Model: openai.GPT4o,
    Messages: []openai.ChatCompletionMessage{
      {Role: "user", Content: userInput},
    },
  })
// El mismo SDK funciona para Claude via compatibilidad OpenAI
📊
Los servicios Go con LLM fallan diferente — necesitan observabilidad diferente
CRITICO en produccion
  • El problema: el servicio puede devolver HTTP 200 con JSON valido, pero el contenido es basura. No hay stack trace, no hay error, no hay alerta con observabilidad estandar.
  • Tracing con spans para el LLM: necesitan saber cuanto tiempo tomo su codigo vs cuanto esperaron al proveedor. Son problemas distintos con soluciones distintas. Atributos necesarios: modelo, tokens del prompt, tokens de respuesta, latencia del proveedor.
  • Logs estructurados que incluyan: user_id, modelo, longitud del prompt, tokens usados, latencia. Sin esto, cuando un usuario reporte "la AI me dio algo incorrecto" no van a poder reproducir que prompt exacto se envio.
  • Metrica de costo = tokens por endpoint en el tiempo. Un cambio de prompt que hace las respuestas 30% mas largas no aparece en ningun lado excepto en esta metrica, antes de que llegue la factura.
  • Latencia del proveedor como histograma (p50/p95/p99), nunca como promedio. Un proveedor con p50=600ms y p99=14 segundos esta arruinando la experiencia del 1% de usuarios — el promedio jamas lo va a mostrar.
  • Errores separados por tipo: rate limit, timeout, respuesta malformada. Mezclarlos no dice que hacer. Separarlos si.
🔄
Circuit Breaker sobre el proveedor LLM — No es opcional
CRITICO Sin esto, una falla del proveedor tumba todo el servicio
  • Sin circuit breaker: cuando el proveedor LLM falla, cada request espera 30 segundos antes de fallar → los thread pools se llenan → otros endpoints sin nada que ver con AI empiezan a fallar tambien.
  • Configurar para abrir despues de 4 fallas consecutivas. Cuando esta abierto, el request falla inmediatamente en lugar de esperar 30 segundos.
  • El circuit breaker se cierra automaticamente cuando el proveedor se recupera. Con GoFr, es configuracion — no codigo.
  • Alertar cuando el circuit breaker se abre: significa que el proveedor tiene problemas antes de que los usuarios lo reporten.
// GoFr: circuit breaker en la configuracion del servicio externo
app.AddHTTPService("llm-provider", "https://api.openai.com",
  &service.CircuitBreakerConfig{
    Threshold: 4,              // abre despues de 4 fallas
    Interval:  1 * time.Second,
  },
)
// GoFr publica app_http_circuit_breaker_state en Prometheus
// 0 = cerrado (ok), 1 = abierto (falla). Alertar sobre esto.

Java + AI — Spring Boot con LangChain4J
Fuente: "Spring Boot + AI Agents: Building Intelligent APIs with LangChain4J and OpenAI" — Medium, Oct 2025
🧠
LangChain4J — el LangChain de Java, ya maduro para produccion
JAVA Para servicios Spring Boot del equipo
  • Agregar LangChain4J al pom.xml y pueden tener un endpoint REST con AI funcionando en menos de una hora.
  • La integracion usa una interfaz Java anotada con @AiService — se inyecta como cualquier bean de Spring. No cambia la arquitectura existente.
  • Memoria de conversacion: con MessageWindowChatMemory el agente recuerda el contexto de la sesion (configurable: cuantos mensajes previos retener).
  • RAG: conectar el LLM a documentacion interna o wikis de MeLi para que responda preguntas sobre sus propios sistemas, no invente respuestas genericas.
  • Caso de uso concreto para su equipo: endpoint interno donde los devs preguntan sobre codigo, documentacion o runbooks de sus servicios. El LLM responde con contexto real del proyecto.
  • Seguridad: las API keys nunca en application.yml en el repo. Usar Spring Cloud Config, el vault de la plataforma, o variables de entorno.
// Asi de simple se ve un AI Service en Spring Boot con LangChain4J
@AiService
public interface BackendAssistant {
    @UserMessage("Sos un experto en este codebase. " +
                 "Responde de forma concisa y precisa.")
    String ask(String question);
}

// Se inyecta como cualquier bean normal de Spring
@RestController
public class AssistantController {
    @Autowired private BackendAssistant assistant;

    @PostMapping("/ask")
    public String ask(@RequestBody String question) {
        return assistant.ask(question);
    }
}
